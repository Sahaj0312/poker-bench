# River Room

A five-seat no-limit Texas Hold’em game for Astra, Opus, Muse, Gemini, and Jev. Watch every seat, read the conversation, and replay a complete session.

## Run locally

Use Node.js 22.9 or newer. Run `npm start` in this directory and open [the local table](http://localhost:4395). The application has no package dependencies. Use `PORT=4396 npm start` to select another port. Run `npm test` for the dealer and integration checks.

The opening table is a reproducible demo paused on the first flop. All five demo seats use the same policy. The player portraits identify seats in both modes. Demo quotes are generated by that policy. Real session quotes come from the players’ responses.

## Connect the five players

Open **Player connections** using the sliders button in the top bar. Enter the exact model IDs you want to compare.

- **Astra** uses a fresh noninteractive Codex invocation for each decision. The default requested model is `gpt-6.2-astra`. Use a current Codex CLI with `--ignore-user-config` support and run `codex login` using ChatGPT. Confirm with `codex login status`. River Room passes only the player view, disables shell, apps, browser, memory and other tool features, discards turns with reported tool use, and runs in an empty temporary working directory. It does not read or copy the login token.
- **Opus** defaults to Anthropic Messages. Supply your chosen model ID and key.
- **Gemini** defaults to Google's OpenAI-compatible chat completions endpoint. Supply your chosen model ID and key.
- **Muse and Jev** accept either an OpenAI-compatible chat completions endpoint or an Anthropic Messages endpoint. Enter the full HTTPS URL, model ID, and key for each. The seat labels are aliases.

The local server stores connections in `data/players.json` with owner-only filesystem permissions. Keys are stored as plaintext on this computer. To supply keys through the environment instead, copy `.env.example` to `.env`. Replay exports contain no keys. Provider URLs must omit credentials and query strings.

Choose **New session**, select **Live models**, choose the format and hand count, then start. Closing the browser leaves live play running while the local server is running. Model calls use the chosen subscription and API accounts. The hosted viewer provides demo play, import, replay and verification. Live model play and credential entry use the local server.

## Fairness and experiment design

- The dealer alone chooses seats and the opening button, shuffles, validates actions, tracks chips and settles pots. A random 128-bit seed is committed with SHA-256 before live decisions. A SHA-256 counter stream, rejection sampling and Fisher–Yates generate each deck using separate deck, position and policy domains.
- All five players receive the same poker instructions and decision schema. Each request includes its own hole cards, public board and stacks, a legal-action menu, and up to the last 80 public history entries. Public showdown cards become available after settlement. Conversation is turn-based and optional. There is no private side channel between seats.
- **Continuous stacks** carries chips and public history across hands, uses a moving button, and finishes at the chosen hand limit or when one seat holds all chips. No rebuys or blind increases. Finishing stacks determine placement.
- **Duplicate deals** repeats each deck and button five times, cycling names through every position. Every hand resets stacks and public history, and provider requests are stateless. Cumulative net chips determine placement. The independent experimental unit for comparing results is a complete five-rotation deal block. A session supplies descriptive results. Estimating a skill advantage requires many independent blocks. Provider-side model behavior, default inference settings and prior training can differ.
- An invalid move, malformed reply, timeout or API error pauses the model run without changing the betting state. Retry explicitly or end the session. Corrected keys for the same endpoint take effect on retry. Model IDs and endpoints are fixed for a session. Model aliases, provider defaults and retries can affect interpretation.
- Every decision has the same 120-second deadline. No automatic fallback to a demo agent. The session metadata records the requested models and endpoints. The CLI and HTTPS API wrappers necessarily differ and provider aliases can change. A replay verifies the dealer and recorded actions. It cannot authenticate who authored a recorded response or prove that an operator published every session they ran.

## Replay and storage

Scrub the timeline, step one event at a time, change playback speed, or jump directly to a hand. After the final event, a summary identifies the leader and the largest pot. **Actions** shows showdown hands and main/side pot payouts. **Fairness log → Verify replay** reruns the dealer from the revealed seed and recorded moves and compares every event.

Live logs are appended to `data/<session-id>.jsonl` on the local server. Sessions interrupted by a server restart remain available as partial replays. Browser demos and imported sessions are kept in IndexedDB. **Export replay** saves JSON. **Sessions → Import replay** opens it again and verifies completed sessions. Exported replays expose all dealt hole cards and table chat.
